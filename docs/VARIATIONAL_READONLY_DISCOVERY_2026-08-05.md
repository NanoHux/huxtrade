# Variational Omni read-only discovery — 2026-08-05

## Scope and safety

- Observed the user's already-authenticated `https://omni.variational.io/` tab through the Chrome extension.
- Did not inspect cookies, local/session storage, passwords, wallet secrets, request headers, or session material.
- Did not submit, cancel, replace, or close an order and did not change leverage or TP/SL.
- Downloaded only public JavaScript modules referenced by the rendered page for static analysis.
- Account values, wallet fragments, transaction IDs, and history values are intentionally omitted from this report.

## Runtime observations

- Current application origin: `https://omni.variational.io`.
- Application API prefix: same-origin `/api`.
- Direct unauthenticated terminal requests to the API returned HTTP 403 (Cloudflare), including public metadata paths. Browser context is therefore required.
- The safe Chrome control surface permits visible DOM inspection but does not expose network request logs and disables page-context `fetch`; raw JSON response schemas were not captured in this pass.
- The authenticated UI successfully rendered portfolio value, initial/maintenance margin usage, market quotes, order tabs, position tabs, and history tabs.

## Authenticated sanitized-HAR results

The Chrome sanitized HAR was processed locally by `discover:har`. The importer discarded all request/response headers and accepted only allowlisted `/api/` traffic. It produced 478 request/response events with mode `0600`.

Verified response shapes include:

- `GET /api/me` → object containing authentication metadata fields (values redacted).
- `GET /api/portfolio?compute_margin=true` → `{ margin_usage: { initial_margin, maintenance_margin }, balance, upnl }`, decimal values encoded as strings.
- `GET /api/positions` → array.
- `GET /api/orders/v2?status=pending` → `{ pagination, result[] }`.
- `GET /api/transfers?...` → `{ pagination, result[] }`.
- `GET /api/settlement_pools/details` → balance, max-withdrawable amount, margin usage, and per-asset/default margin parameters.
- `GET /api/settlement_pools/existing` → settlement-pool identity and both counterparties' margin parameters (identity values omitted/redacted).
- `POST /api/settlement_pools/leverage` with `{ assets: string[] }` is a read/query request despite POST semantics.

Direct unauthenticated terminal requests returned 403 while the same paths succeeded inside Chrome, confirming that the production adapter must preserve the authenticated browser context rather than copy credentials out of it.

## Approved minimum-size live verification

An explicitly approved BTC-PERP lifecycle test was completed with 5x leverage:

- Entry: market sell `0.00077 BTC` at `$64,196.29` (about `$49.43` notional and `$9.88` required margin).
- Entry maximum slippage: `0.5%`.
- Take profit: full-position close-only buy, mark trigger `$63,500`, maximum slippage `3%`; observed `Pending` after entry.
- Stop loss: full-position close-only buy, mark trigger `$64,800`, maximum slippage `3%`; observed `Pending` after entry.
- Exit: immediate market buy `0.00077 BTC` at `$64,207.45`, maximum slippage `1%`.
- Post-exit reconciliation: no BTC position; both protection orders changed to `Canceled`; both entry and exit trades were `confirmed`.
- Realized PNL displayed by Omni: `-0.01 USDC`.

No residual BTC position or pending BTC protection order remained after the test.

A second capture-focused run using the same parameters was completed while Chrome Network recording was enabled:

- Entry: market sell `0.00077 BTC` at `$64,253.64`.
- TP/SL: mark-triggered `$63,500` / `$64,800`; both observed pending, then canceled automatically after close.
- Exit: market buy `0.00077 BTC` at `$64,248.79`.
- Both trades were confirmed, no position or pending BTC protection order remained, and the UI displayed realized PNL as `0.00 USDC`.

## Adapter implementation result

- Added a production-shaped `browser-fetch` adapter that keeps authentication inside a dedicated Chrome/Playwright or loopback-CDP context and only permits same-origin `/api/` calls.
- Implemented portfolio/margin reads, leverage verification, indicative quoting, quantity tick/minimum handling, limit entry with attached TP/SL, pending-order cancellation, position/trade/realized-PNL reconciliation, and quantity-scoped reduce-only emergency close.
- A missing TP or SL RFQ ID fails closed and invokes the existing cancellation/emergency-close compensation path. An interrupted `SUBMITTING` process restarts as `UNKNOWN` and is never resubmitted automatically.
- Full repository verification passed: 8 test files / 35 tests, all workspace type checks, and the production build.
- A native read-only smoke run opened the dedicated project Chrome Profile successfully, but that Profile was not logged in; the Agent reported `loggedIn=false`, `reconciled=false`, and blocked trading. The user's ordinary Chrome session was deliberately not copied or inspected.

Remaining live checks are limited to limit-entry lifecycle, active cancel response, ambiguous mutation timeout/rate-limit behavior, and natural login expiry/re-login. `LIVE_TRADING_ENABLED` remains `false`.
